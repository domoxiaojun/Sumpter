# 双端引擎架构分析

> 2026-08-30 · 逐处裁定数据见 `parity-ledger.md` · 本轮修复记录见 `plan.md`

## 摘要

`macos/crates` 与 `linux/crates` 是两份同源副本。实测**真正平台专属的 Rust 只占 2.8%**
（约 1200 / 42274 行）。按这个比例，业界不存在维护两份引擎的先例 —— Chromium 的 `//base`
平台专属比例远高于此，它也只有一份。

**结论：能改成"一份引擎 + 条件编译 + 边界注入"，而且这个代码库已经在用注入模式**
（`Arc<dyn UpstreamTransport>`、`Option<ConfigDir>` 都是注入进来的），是扩展而非引入。

阻塞点不在代码，在仓库拓扑：`linux/` 要当独立仓库的根（GitHub 才能发现
`.github/workflows/`）→ 发布必须用合成提交拼形状 → 共享 crate 在两种布局下需要两种 path 值
→ 只能各存一份副本。**这条链的第一环是自己选的，不是外部约束。**

## 1. 测量方法（可复现）

```bash
# 原始差异
diff macos/crates/<path> linux/crates/<path> | grep -c '^[<>]'

# 归一化差异 = 去注释、压空白、去空行 → 近似语义差异
# 注意 grep 必须用 '^[[:space:]]*$'：只写 '^$' 会漏掉「只含空白的行」,
# 注释被剥后残留的缩进会被算成真差异,数字整体偏高。
norm() { sed -e 's|//.*$||' -e 's/[[:space:]]\+/ /g' -e 's/^ //;s/ $//' "$1" \
         | grep -v '^[[:space:]]*$'; }
diff <(norm macos/crates/<path>) <(norm linux/crates/<path>) | grep -c '^[<>]'
```

`impl Engine` 的方法体逐个对拍见 `parity-ledger.md` 的复现段。

## 2. 分层实测

### 2.1 文件级三态

| 状态 | 文件数 | 文件 |
|---|---|---|
| **A1 逐字节一致** | **13** | `access` `bridge_in` `core/lib` `model_name` `scheduler` `warnings` `tests/bridge_in` `tests/golden` `tests/retry_policy` `tests/routing` `health` `outbound` `runtime_store` |
| **A2 归一化一致**（仅注释/空白不同） | **7** | `bridge` `config` `routing` `request_build` `stream_terminal` `events` `runtime_query` |
| **仍有逻辑差异** | 7 | `admin` 3395 · `tests/engine` 1754 · `engine` 1406 · `main` 518 · `config_store` 430 · `server` 70 · `proxy/lib` 1 |

**门禁可覆盖 20 / 27 个文件（74%）。**

### 2.2 门禁必须两级，逐字节不够

有些文件**永远无法逐字节一致，因为注释必须描述各自平台**。`config.rs` 是典型 —— 14 行差异里
9 行有意：

- 文件头：macOS 写「config.json 由 SwiftUI 壳负责编辑与写盘」；Linux 写「Admin PUT 是唯一远程
  写入口，reload/SIGHUP 只读磁盘」。两段各自准确。
- `/// 兼容旧 SwiftUI/测试命名` vs `/// 兼容旧 WebUI/测试命名`。同理。

强行统一等于让文档变得不准确来迁就门禁。所以 **A2（归一化 cmp）同样是正式门禁级别** ——
它挡住全部逻辑漂移，那才是目的；逐字节只是手段。

### 2.3 子系统体量

| 子系统 | 生产码 | 归一化差异 | 反向依赖 |
|---|---|---|---|
| 统计（`runtime_store` + `runtime_query`） | 9928（= `kekulv-proxy` 的 **54%**） | **0** | **零** —— 都不 `use` engine/server/outbound/request_build |
| 引擎（`engine.rs`） | 5560 | 1406 | — |
| 管理面（`admin.rs`） | 2046 / 4438 | 3395 | — |

统计子系统占一半代码量、零差异、零反向依赖 —— **抽 crate 是纯收益，零重构风险**。

## 3. `engine.rs` 差异构成（1406 行逐项归属）

| 归属 | 行数 | 性质 |
|---|---|---|
| 通知链路：9 个顶层 fn（154）+ 7 个 `NOTIFY_*` 常量 + `handle_notify`(148) + `should_emit_notify`/`recent_claude_failure`(51) + 相关 import/字段 | ~520 | macOS 独有特性 |
| `Engine::new` / `EngineInner` 字段接线（`notify_dedup`、`migration_notice`、`control_token`） | ~168 | 上一条的构造侧 |
| 控制端点：`handle_status`(32) + `handle_reload`(25) + `control_token`/`loopback_or_token`/`query_token_ok`(15) | ~130 | macOS 独有数据面控制口 |
| `PlanMeta` trait + impl(45) + `record_rejected_client_with_id_and_metadata`(53) + `ClientMeta` 就地构造(22) | ~190 | 结构选择，非平台必需 |
| 纯噪音：局部变量名（`nt`/`vt` vs `name_truncated`）、参数名（`id` vs `request_id`）、字面量 vs 命名常量、常量声明顺序 | ~210 | 可消除 |
| **真逻辑差异** | **21** | 见 §3.2 |

**1385 / 1406 只归因于四个可命名的特性包 + 命名噪音。** 这不是"两个实现漂移了"，
而是"一个实现 + 一个可选特性包 + 一处结构选择 + 噪音"。

### 3.1 hunk 分布支持这个判断

150 个 hunk 中：

- **10 个 ≥20 行 → 816 行（58%）** —— 集中，且逐一归属到上表前四项
- 49 个 ≥5 行 → 1196 行（85%）
- **101 个 1–4 行碎片 → 仅 210 行（15%）** —— 抽样确认几乎全是通知特性的成员散落在 import 块
  与 `EngineInner` 字段里，加命名噪音，**不是逻辑弥散**

差异集中而非弥散，是 cfg / 注入可行的前提。

### 3.2 唯一的真逻辑差异（21 行，待裁定）

`handle_messages` 里对 `RoutingRequest::from_value(&parsed)` 的处理：

- macOS：`let Some(request) = … else { 记 400 BODY_NOT_OBJECT + 返回 400 }`
- Linux：`.expect("validated Anthropic Messages request is a JSON object")`

已核实前提：两侧 `valid_anthropic_messages_request` **逐字节相同**，都在此调用之前执行，
且用 `value.as_object().is_some_and(…)` 保证是对象；而 `from_value` 的唯一 `None` 路径就是开头
的 `value.as_object()?`。所以 **Linux 的 `expect` 可证不可达，macOS 的 400 分支是死代码**。

两侧都不误动作，但：

- macOS 的 `message_tokens::BODY_NOT_OBJECT` 在 `/v1/messages` 路径上**永不可能出现** ——
  凭这个 token 排查问题会被误导
- Linux 把不变量收紧成断言，代价是一旦前置校验被削弱就 panic（代理数据面 panic 比 400 严重）

倾向：保留 Linux 的断言（idiomatic 且自文档），删掉 macOS 的死分支，并在 `spec-engine.md`
记明该 token 不适用于 Messages 入站。

## 4. 根因

**不是分叉失控，而是没有机制证明哪些是一致的。**

实质漂移只有 3 处功能级 + 6 处测试级（本轮已全部修掉）。但因为四万行代码平等地躺在两个副本里，
每次改动都要重审全部 —— 注意力被均摊到 4 万行，真正该盯的 6000 行反而没有专门约束。

更严重的两个结构空洞：

1. **`macos/crates` 在 PR 阶段零 CI 覆盖。** `ci.yml` 在仓库根（= Linux）跑
   `cargo check --workspace`，`macos/` 子目录只有推 `v*` tag 时才被 `macos-release.yml` 碰到。
   漏改不仅没人拦，连编译错都要等到发布。该目录**零平台专属依赖**，ubuntu runner 就能跑。
2. **`RUST_UPSTREAM.md` 的差异表是人工维护的**，无法发现测试名漂移，且当轮已过期 8 天
   （`admin.rs` 从表里的 ~2680 涨到 4290）。

## 5. 业界对照

几乎没有项目为每个平台维护一份引擎副本。主流做法是**一份引擎 + 文件级条件编译 + 边界注入** ——
平台差异落在"哪些文件参与编译"，而不是"哪份代码库"。

| 项目 | 做法 |
|---|---|
| **Rust 标准库** | `library/std/src/sys/pal/{unix,windows,wasi}/` —— 一份 std，平台实现在各自目录，cfg 选目录 |
| **Chromium** `//base` | `file_util_posix.cc` / `file_util_win.cc`，`BUILD.gn` 按平台挑 sources |
| **Go 生态**（Tailscale、Syncthing、Docker） | 文件名后缀 `_linux.go` / `_darwin.go` + build tags，编译器按名字选 |
| **Signal** | `libsignal` 是单独一个 Rust 仓库，Swift/Kotlin/TS 客户端通过 FFI 消费。引擎字面意义上只有一份 |
| **Mozilla application-services** | Rust 组件 + UniFFI 生成 Swift/Kotlin 绑定 |
| **Bitwarden** | 客户端逻辑收进 Rust SDK，各平台客户端共用 |

Dropbox 当年用 Djinni 做 C++ 核心 + 生成绑定，后来在移动端放弃了共享 C++ —— 但放弃的是 UI 层
共享，**同步核心始终一份，没有分叉成两个副本**。

## 6. 目标架构

### 6.1 依赖级选择优于 cfg

把通知链路和控制端点做成**独立 crate**，Linux 的 `kekulvd` 就是不依赖它：

- Linux 二进制里**根本不存在**那些符号，编译器保证，不靠 cfg 正确性
- 不用维护 cfg 组合的测试矩阵
- 躲开一个真实陷阱：**Cargo feature 统一化**。若用 `feature = "notify"` 区分且两个产品在同一
  workspace，`cargo test --workspace` 会取 feature 并集，把 notify 编进 Linux 构建 ——
  `linux_data_plane_has_no_control_or_notify_write_endpoints` 会直接失败

cfg 只留给真正必要的少数地方（如 sidecar 的 stdin EOF 判父死，那在 bin crate 内部）。

### 6.2 `/__` 404 不变量靠注入即可复现

Linux 现状：

```rust
"/__status" => self.handle_status(&config, remote_text.as_deref()),
"/__runtime" => 404,
"/__reset-stats" | "/__reload" => 404,   // 数据面不留旁路
_ => 404,
```

注入后：`/__status` 留在共享引擎；`/__notify`/`/__reload` 进注入的控制面；Linux 传 `None`
→ 落 `_ => 404`。**行为逐字复现，零 cfg。** 而且不变量测试变成"构造无控制面的引擎并断言 404"，
两侧同一套测试都能跑 —— 比现在更强。

### 6.3 目标形状

```
crates/kekulv-core/          一份，零 cfg
  config_store.rs            ← ConfigDir 已是注入值；平台策略(keys.json 拒启)变参数

crates/kekulv-proxy/         一份
  engine/
    mod.rs                   Engine 结构 + 构造(接受注入)
    inbound.rs               3 个入站处理器      ┐
    forward.rs               forward/relay/race  │
    events.rs                record_*/complete_* ├ 共享，进 A1 门禁
    capture.rs               诊断捕获            │
    persist.rs               flush_*             │
    runtime_api.rs           26 个统计委托       │
    status.rs                /__status           ┘
  control.rs                 trait ControlSurface（接口）

crates/kekulv-notify/        macOS-only crate
  通知链路 + /__notify + /__reload，实现 ControlSurface

crates/kekulvd/              共享装配 lib
crates/kekulvd-macos/        薄 bin：sidecar 握手 + 注入 notify
crates/kekulvd-linux/        薄 bin：前台/SIGHUP + 不注入 notify
```

### 6.4 注入面（已有两个，是扩展而非引入）

| 注入什么 | 现状 | 目标 |
|---|---|---|
| 上游传输 | `Arc<dyn UpstreamTransport>` ✓ 已注入 | 不变 |
| 配置目录 | `Option<ConfigDir>` ✓ 已注入 | 不变 |
| 控制面 | `control_token: String`（仅 macOS 签名有） | `Option<Arc<dyn ControlSurface>>` |
| 通知 | 硬编码在 `engine.rs` | 由 control surface 承载 |

`impl Engine` 现为 **3696 行 / 91 个方法**，其中真正的请求处理只有 11 个；统计委托 26、
诊断捕获 17、刷盘 6、事件记录 6、配置生命周期 8。拆模块的边界是现成的。

## 7. 三条合一路线

| | 做法 | 成本 | 收益 | 风险 |
|---|---|---|---|---|
| **1. monorepo 形状 = 发布形状** | 把 `linux/*` 移到根，`crates/` 成为唯一一份，`macos/` 只留 Swift + 平台文件 | 1 天 + 决策 | **合成提交仪式整个消失**；共享 crate path 只有一种形状；三个问题一次解决 | 根目录内部文档会公开（`CLAUDE.md`、`todos-*.md`、`parity-ledger.md`、`scripting/`）。`.control_token` 已 gitignore，不受影响 |
| **2. 共享 core 独立成仓**（Signal 模式） | Cargo `git = …, rev = …`，本地开发 `[patch]` 覆盖 | 中 | 现有拓扑不动 | 三个仓库；每次改核心要先推 core 仓再更新两侧 rev。单人项目偏重 |
| **3. 一份真源 + 生成副本 + CI 校验** | 保持拓扑，加生成步骤 | 低 | 机器保证一致 | 仍是两份文件，只是不再靠纪律 |

**三条路线的共同前提：先拆模块。** 每个业界例子都依赖同一件事 —— 平台专属代码必须是**文件形状**
的，cfg 才能按文件选，Go 才能按后缀选，`BUILD.gn` 才能按平台挑 sources。而现在通知链路和控制
端点是**嵌在 3696 行 `impl Engine` 里的方法**。

## 8. 实施顺序

```
① 门禁（A1/A2 cmp + 测试名对称白名单 + 分叉棘轮）   1 天    ← 安全网，必须先立
② 补 macOS PR CI                                    1 小时  ← 补最大的覆盖空洞
③ 拆 engine 模块（notify/control 独立成文件）        2–3 天  ← 三条路线的公共前提
④ 通知/控制抽 crate + ControlSurface 注入            2–3 天
⑤ config_store 注入化（keys.json 策略变参数）         1 天
⑥ 抽 kekulv-runtime crate（9928 行，零反向依赖）      1–2 天
⑦ 仓库拓扑合一 + 删掉合成提交仪式                     1 天    ← 需要公开边界决策
⑧ 合并测试套件                                      2–3 天
```

**①–⑥ 完全不需要动仓库拓扑。** 即使最终放弃 ⑦，做完 ①–⑥ 后：

- 引擎的平台专属代码物理隔离在 Linux 侧不存在的文件里 —— 不可能漏改，因为没有对应文件可改
- 剩下的共享部分全部进 A1/A2 门禁
- 结构税从"每次改引擎要改两次并自己记得"降到"漏改立刻红"

⑦ 只是把"两份机器保证一致的副本"变成"一份物理文件" —— 锦上添花，不是必需。

**`admin.rs` 可以不动。** 它不是引擎；共有 28 条 route 的处理器虽可共享（macOS 的 28 条是
Linux 39 条的子集），但拆分收益低于 engine，留给棘轮盯着即可。

## 9. 不建议

- **单文件 + cfg feature**：只多买到"命名噪音也统一"，却要引入生成管线 + cfg 组合测试矩阵，
  且 650 行通知包套 cfg 显著伤可读性
- **覆盖式从一侧拷到另一侧**：`RUST_UPSTREAM.md` 已禁止，会盖掉 Linux 的 Admin 鉴权
- **合并两套前端**：Swift 统计 UI 6216 行 vs WebUI 13778 行，SwiftUI 与 React 无共享面

### 两条方法论教训

1. **判定"不可复刻"前先分清"平台强加的差异"与"一侧的实现偏差"。**
   `ingress_preflight_never_polls_…` 原判不可复刻，理由是 macOS 的 `handle_request(body: Bytes)`
   让"不读 body"无法断言 —— 但那个签名本身就是缺陷。修掉之后测试自然可复刻了。
2. **先比函数体，再断言"这是改名"。** 三对"同测试改名"里只有一对真是改名：另一对是
   **两个不同场景**（401 vs 502，502 走 deferred，语义不同），当成改名合并会丢一个；
   第三对是有意的组织差异。
